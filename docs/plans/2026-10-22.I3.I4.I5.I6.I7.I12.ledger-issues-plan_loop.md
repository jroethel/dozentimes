## Shape and validation

The chain is strictly serial, one child per wave, because T1 to T7 all modify `freshtime-agnt/ledger.ts`.

```
orchestrator (cez/ef186bfa)
  |- commit unit test edits -> dispatch child Tn -> poll (sleep 60) -> merge -> re-run check
  |- T1 -> T2 -> [A] -> T3 -> [B + C] -> T4 -> T5 -> T6 -> T7 -> T8 -> [D] -> /loop-review
```

Three validation layers:

1. Implementer self-check: the child runs the unit's tests and acceptance check before it commits.
2. Gate re-run: the orchestrator merges the child branch and re-runs the full acceptance check itself, including the replay pair for T1 to T3.
3. Human checkpoints A, B, C and D from the source plan, asked as JRIT-ASK cards.

## Hazards and deviations

- Branch (deviation): the source plan says all work is on `feat/pi-time-poc`.
  In this run the integration branch is `cez/ef186bfa`, which already contains `feat/pi-time-poc`.
  A child commits only on its own cezar branch and never checks out or commits to `feat/pi-time-poc` or `main`.
- Check custody (deviation): the orchestrator commits each unit's test edits, verbatim from the source plan, on the integration branch before dispatching the unit.
  Test files are outside the child's ownership, and a child diff that touches them is a scope violation.
- Replay drift (deviation): the replay corpus is every git repo under `~/create` and `~/repos`, which moves whenever any of them gets a commit.
  The replay gates for T1, T2 and T3 are judged on a before and after pair the orchestrator runs back to back at the gate: before from the pre-merge integration tip, after from the merged tip.
- Sample text (deviation): `--show-sample` prints fact text, and a cezar transcript is a file.
  No session in this run prints a sample; a child may only pipe it to `wc -l`.
  At checkpoints A and B the card hands Jeremy the exact command to run in his own terminal.
- Disjoint files: one unit per wave, so no merge conflict is expected; a conflict at a gate is a scope violation and stops the run.
- Dirty tree: every child forks from a committed tip; the orchestrator commits before each dispatch.

## Wave loop

For each unit in order:

1. Commit the unit's test edits from the source plan on the integration branch, with this file and the journal current.
2. Claim the unit's issue (`bash <loop-drive>/scripts/receipt.sh claim <num> <session>`) and dispatch the child with the template below.
3. Post `AGENT STATUS branch=<b> child=<id> verdict=pending repairs=0` on the issue, and log the child id and branch in the handoff file.
4. Poll the child once a minute until it is done or failed.
5. Gate: for T1 to T3, run the before replay; then `git merge --no-edit <child branch>`, re-run the acceptance check, and for T1 to T3 run the after replay and the compare command.
6. On a failed check, send the itemized failure to the child once through the cezar continue call, then re-merge and re-check; a second failure stops the unit.
7. Post the gate's `AGENT STATUS`, append the journal, commit, and advance only on a green integration branch.

Issue per unit: T1 #3, T2 #12, T3 #7, T4 #6, T5 #3, T6 #4, T7 #5, T8 #3.
An issue is marked done through the receipt helper with `--ran` only after its unit's gate and checkpoint pass; #3 is marked done after checkpoint D.
Receipt bodies carry branch, child id and verdict only, never fact text, because the repo is public.

Ask-the-human list:

- Checkpoint A after T2, B after T3 (with C asked in the same card), D after T8.
- A merge conflict, a second failed check, a stuck child, or a spec edit larger than 15 lines or touching more than one unit.

After T8 and checkpoint D, run the advisory `/loop-review 8e34055` from the integration branch and record its findings in the journal.

Durable state lives in git (`cez/ef186bfa`), the journal, the cezar handoff file, and each issue's `AGENT STATUS` comments.
A child keeps running when the orchestrator stops.
To resume, list this task's children with the cezar runs API, send each finished child to Gate and each unfinished one to Wait, and dispatch only units with no child.
A unit whose child failed or vanished is relaunched from scratch, never resumed.
