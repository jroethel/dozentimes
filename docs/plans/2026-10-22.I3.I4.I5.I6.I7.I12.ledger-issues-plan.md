# Ledger Issues (#3, #4, #5, #6, #7, #12) Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its
> acceptance check passes. No specific tooling, harness, or skills are assumed.

**Goal:** Close six open ledger issues on `feat/pi-time-poc` so replacement, verification and shelf lives match what the docs and the person actually say.

**Approach:** One prefactor first: every closed fact records which rule closed it, which #3, #6, #7 and #12 all need.
Then the replacement rules are fixed in order of blast radius (#12 narrows rule (d), #7 adds a status-family rule, #6 matches reworded lines), then the person's statements become verifications (#3), shelf lives are fitted from the checks those produce (#4), and keyword-classified rows are upgraded in `maintain` (#5).
A final pi end-to-end task proves the statement path through real pi.

**Tech stack:** TypeScript on Node 26 (type stripping, no build step), `node:sqlite` with FTS5, `node --test`, chrono-node, Jev over fetch (optional), pi in RPC mode for the end-to-end suite.

**Source brief:** none.
The six GitHub issues are the spec: `gh issue view <n>` for 3, 4, 5, 6, 7, 12.

## Global constraints

- No extracted personal facts, ledger databases, or copied doc text enter git.
- The ledger DB lives in `~/.freshtime/` (outside the repo).
- Test fixtures are synthetic files that imitate the real formats.
- Replay output stays under `~/.freshtime/replay/` and holds counts and rates only.
- All work is on branch `feat/pi-time-poc`, one commit per task, no push, no merge to main.
- Commit messages are plain sentences with no co-author line.
- Human-read docs (`*.md` prose, `learning_guide.html`): never the em dash character, one sentence per physical line, pipe tables padded to aligned columns and at most 110 characters wide.
  Machine-read files (JSON fixtures, `results.json`, trace lines) are exempt.
- No new npm dependencies.
- Every path works with `FRESHTIME_JEV=off`; Jev stays optional.
- `npm test` ends every task with `fail 0`, and the todo count only goes down (baseline 2026-10-22: tests 63, pass 52, fail 0, todo 11).
- Tracker labels and issue closing are done by whoever drives this plan, never inside a task.

Rationale for the calls that are easiest to get wrong:

- D1: the 2026-10-22 replay found that all 1842 unique rule (d) cases crossed into a different file with a different slug.
  Across 305 real handoff files, only 4 of 301 filename slugs recur on more than one date, and 19 files name another handoff in the same directory.
  Slug-only scoping would leave rule (d) nearly dead, and the naming reference catches resume chains.
  Most real handoffs are per-task resume pointers (`## State`, `## Next step`, `## Recent artifacts`), so project-wide (d) let one task's State close another task's.
- D2: the old todo fixture used slugs `a` and `b`, which can never pass under D1, and the ledger stores no time of day.
  The naming reference gives a direction without a clock.
- D3: #3 needs to tell a user close from a removed line (the reopen at `freshtime-agnt/ledger.ts:162` would otherwise undo it), #6 needs to tell a rewording from a change in `verifyFact`, and the replay report can read the column instead of guessing the rule from text.
- D5: a fact with a made-up file path would be closed by rule (c) or by `verifyFact` as "file missing" the first time it went stale.
- D8: `checks` rows from source re-reads only exist for facts already past their shelf life, so the data is censored.
  User statements are excluded from the fit and reported separately, because the person mostly speaks up when something changed, which would bias the fit.
  The minimum counts distinct facts, because 30 checks of one fact are not 30 observations.
  0.25 is a policy number, so Jeremy decides it at checkpoint C, before T6 is built.
- D9: one Jev chunk can wait 30 seconds, so reclassifying thousands of rows at pi startup during a Jev outage would stall startup for minutes.
  A limit of 40 is one chunk, so `/freshtime maintain` waits at most 30 seconds during an outage.
- D10: the tightest real near-misses are one-word changes ("Next: write the lantern parser" to "...tests" is 0.67, "Waiting on the orchard schema review" to "...exporter review" is 0.71).
  Next:, checkbox and status-family lines are excluded because their own rules own them.
  Length alone does not protect a long line: a changed port number in a 12-word line scores 0.85 and an added "not" scores 0.91, so number tokens and negation words must match exactly.
- D11: "Waiting on the vendor price sheet" and a later "Waiting on the DBA for credentials" are two open dependencies, so a later wait alone must not close an earlier one.
  The text after the prefix must overlap: the #7 fixture pair ("the orchard schema review", "the orchard exporter review") scores 0.60, and the vendor and DBA pair scores 0.14.
- D12: a narrative bullet ("merged the parser on Tuesday") records an event that stays true, so replacing it would be wrong.
  Staleness of narrative is left to shelf lives.
  This narrows #7's "Still open" sentence and needs Jeremy's yes or veto.
- D15: the replay suite's rule is that no fact text is written or printed, because the repo is public.
  The replay gates count how often a rule fires, not whether it fired correctly, so a person has to grade a sample.
  Jeremy allowed text on the terminal only, behind an explicit flag.

B. After T3: rule (e) correctness and D12.
   Jeremy grades the 20 `status_family` closures from `--show-sample status_family`, and says yes or veto to D12 (narrative bullets in older handoffs stay unreplaced).
C. Before T6: D8.
   A fitted shelf life targets a 0.25 chance that a fact has changed by the time it goes stale.
   Replay data from 2026-10-22 puts status facts at 0.07 changed by 7 days and 0.35 by 31 to 90 days, so if live checks look like that replay, the fit would lengthen the status shelf life from 7 days to somewhere between one and three months.
   Combined with D1 (fewer handoff replacements) and D12 (no narrative replacement), the ledger would show more facts as current for longer.
   Jeremy confirms 0.25 or sets another value, which T6 then uses.
D. After T8: the end-user check.
   Jeremy runs `./pi-time/pi-time` on his real docs, tells it one fact changed, asks about it again, then says the old fact still holds and asks again.
   This is the check the automated suites cannot make, because the e2e suite runs on synthetic fixtures.
   The driver files a follow-up issue for D6: a later doc edit should be able to close a conversation fact.

**Interfaces:**
- Consumes: `closed_by = 'handoff_section'` from Task 1.
- Produces: rule (d) with this contract.
  - `handoffSlug(path)` (exported): the basename without `.md`, then without a trailing `.resume`, then without a leading `YYYY-MM-DD` and one following `.`, `-`, `_` or space.
    `HANDOFF.md` has slug `HANDOFF`.
  - Handoff H continues handoff E when both are handoffs (`isHandoff`) in the same project, E is not H, and either `slug(E) = slug(H)` and E's date is earlier than H's, or H's file text names E and E's date is not later than H's.
    H names E when E's basename without `.md` starts with a `YYYY-MM-DD` date and appears in H's text with no letter, digit, `_` or `-` directly before or after it.
    A handoff's date is the `valid_at` of its facts.
  - For each state-like section name (`STATE_SECTION`, compared lowercase), every live fact in that section of E is closed by the latest H that continues E (latest by date, ties by path order): `invalid_at` = that H's date, `replaced_by` = the first fact of the same section in H, `closed_by = 'handoff_section'`.
  - The result does not depend on ingest order.
    When the file being ingested is E, the naming check reads the other handoffs' text from disk (`existsSync` and `readFileSync` on their `source_path`), each file at most once per `ingestCore` call.
  - Two handoffs with the same slug and the same date never replace each other.
  - Replay's `slugOf` is replaced by `handoffSlug`, so its "diff slug" count uses the same rule.
    Name-chain cases still count as "diff slug" there.

- Produces:

```ts
export interface ShelfLife { days: number | null; n: number; facts: number; user: number; fitted: boolean }
export const MIN_FACTS = 30;
export const P_STALE = 0.25; // Jeremy's value from checkpoint C
export function shelfLives(db: DatabaseSync): Record<Volatility, ShelfLife>;
```

  - Observations for a class are the `checks` rows with that `checks.kind`, `age_days >= 1`, and a reason that does not start with `user:`.
    `n` is their count and `facts` the count of distinct `fact_id` among them.
    `user` is the count of `user:` rows of that kind, reported and never fitted.
  - Below `MIN_FACTS` distinct facts: `{ days: SHELF_LIFE_DAYS[kind], n, facts, user, fitted: false }`.
  - Otherwise, fit λ by maximizing `L(λ) = Σ changed·ln(1 − e^(−λ·age)) − (1 − changed)·λ·age` over λ in [1e-4, 10] by a search on log λ, precise to 1% or better.
    `days = clamp(floor(−ln(1 − P_STALE) / λ), 1, 365)`, `fitted: true`.
  - `summary(db, now)` returns the map as `lives`.
    `needsCheck` uses `lives[kind].days` (NULL never goes stale).
  - Replay's freshness table keeps the hand-set `SHELF_LIFE_DAYS`, because it measures them.
