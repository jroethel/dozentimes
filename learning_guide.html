1. Project summary and scope

Two time tools share one contract, and pi-time runs both inside pi.
freshtime-intf turns a question plus conversation state into a TemporalIntent (as-of mode, anchor, basis). freshtime-agnt is a freshness ledger of dated facts with a volatility class, last-verified date and status. freshtime-core holds the contract, SQLite schema, traces and Jev client. ./pi-time/pi-time launches pi with its own agent dir and the freshtime extension.
The design is the "Two tools, one contract" sketch from research/memory-systems-oct2026/time-coverage.html, built backwards from a test.
The ledger reads Jeremy's own project docs and keeps the result outside the repo.
Sources are whats_next.md, HANDOFF.md, docs/handoffs/*.md and learning_guide*.html under ~/create and ~/repos. The ledger lives at ~/.freshtime/ledger.db.
The repo stays public at Jeremy's choice, so no extracted fact, session transcript or auth link may enter git.

2. Architectural principles that emerged

Code finds candidates and does date arithmetic, Jev only judges.
chrono-node parses date phrases. Jev picks the as-of mode, picks an anchor from the parsed candidates (never writes a date), and answers whether a question changes the period. Every Jev call has a deterministic fallback.
A fact is last confirmed when its author wrote it, not when the ledger read it.
At ingest last_verified_at is the fact's valid_at and verified_by is author. Only a source re-read moves it to today with verified_by = source.
Found in the first interactive run on 2026-10-22: the status line said "0 stale" across 809 facts because ingest stamped every fact as verified today. After the fix, 342 were stale.
An inherited as-of date survives unless the question changes the period.
Jev's mode choice cannot override an inherited reading. Only the "does this question change the period" judgment can.
Live Jev read the follow-up "And the next step for alpha?" as a future question and dropped the inherited 2026-10-14, which made the Jev ablation lose one question. The fallback rules had it right.
Handoffs are snapshots, so a later handoff's state section replaces the earlier one.
State-like sections (State, Next step, Recent artifacts, Open ...) in a later-dated handoff of the same project replace that section in earlier handoffs. Within one file, an earlier same-day Next: line is replaced by a later one.
Before this rule, 0 of 809 real facts were ever replaced, because real handoffs use section headings where the rule only knew Next: lines. After it, 48 were.
Every Jev failure is loud.
A failed call writes a trace row with the error, the status line shows jev FALLBACK n, and /freshtime trace shows the row as ERROR. The answer still arrives on the fallback path.
Checked on 2026-10-22 by launching pi-time with a bad TYPESAFE_API_KEY.

3. Design-process learnings

Score fact choice, status labels, harm and re-reads separately, or the 1+1=3 result is rigged.
A single "right fact with the right status" score gives each tool half of a conjunction, so a positive interaction is guaranteed by construction. Measured separately, status accuracy only adds up (interaction 0.00), and harm drops by more than the sum (interaction -2).
Raised by the advisor before the test was written. The honest result is the stronger one: the ledger alone removes no harm, because it shows the newest fact as true for past questions.
Re-read spend depends on question order, so it needs a cold mode.
In the carried script, one early "now" question freshens the facts later questions use, so ledger-only and both spent the same 4 re-reads. With a fresh ledger per question (--cold), ledger-only spends 24 and both spend 9.
The first test asserted both.checks < agnt.checks on the carried script and would have failed. The assertion moved to the cold run, where it measures what it claims.
A score on labels written next to the rules is a regression check, not accuracy.
The rules scored 20/20 and Jev 19/20 on 20 labeled intent questions, but the labels and rules came from the same worker. Issue #1 asks for a blind set.
Assert the mechanism, not a coincidence of the fixtures.
An early assertion agnt.harm == none.harm held only because the two were wrong on different facts. The test now checks per question: ledger-only has harm on the past and inherited questions (q2 to q4) and none on the "now" one (q1).

7. Operational learnings

Run pi in json mode with stdin closed.
pi --mode json ... < /dev/null. Without the redirect it hung from a non-TTY harness. Assert on tool_execution_end records.
In the TUI, never mirror extension output to stderr.
Stderr lines tear the pi screen. The extension writes to stderr only when ctx.hasUI is false.
Test the first run on a throwaway ledger so the real first run stays a first run.
Every E2E used FRESHTIME_DB in $TMPDIR. ~/.freshtime does not exist yet.
pi rewrites its settings file.
pi adds lastChangelogVersion to pi-time/agent/settings.json, so the committed copy includes it.
A herdr side pane is the closest thing to Jeremy's own first run.
herdr pane run to launch, herdr agent prompt --wait to ask, herdr pane read to see the screen. This is how the stale count, the torn screen and the fd download were found.

8. Updates - test suites (2026-10-22)

"Line still in the file" is not "still true" for logs and handoffs.
The first replay counted every rule replacement of a line still present as a miss, and reported recall 0.53. whats_next.md keeps old Next: lines below newer ones, and handoff folders keep old files. With rule replacements counted separately, recall against git is 0.998.
Caught by the orchestrator reading the first replay report, before the numbers reached an issue.
A replacement closes at its successor's date, not the newest one's.
Rule (b) closed every older Next: at the newest date when a file was read in one pass, so a past read between sessions showed a stale step. Found by test/kinds/valid.test.ts, fixed by chaining each one to its successor.
A removed line that comes back must be reopened.
The unique key (source, section, text) made a re-added line skip insertion and stay invalid. This caused 1,998 replay misses. It is now reopened. The gap between removal and return is lost (a ponytail: comment marks it).
Explicit "now" words beat Jev's mode.
In the e2e suite, live Jev read "What is the next step for alpha now?" as future. With no date in the question, a "now" word is a stated reading that Jev cannot override. This is the second guard on Jev after the inherited-as-of guard.
On every labeled set so far, Jev's intent reading adds nothing over the rules. Its value stays untested until the blind set (#1).
A judge question has to ask about the time the question asks about.
"Does the answer present X as currently true?" failed correct historical answers that also mentioned the present. The e2e judge now asks whether X is presented as true for the asked date or period, and whether a fact is included in any wording.
The 7-day status shelf life is too short on real data.
The replay with Jev classes found 4,672 status facts flagged and 14% of them changed in git. The share changed was 7% at 0 to 7 days and 35% at 31 to 90 days. The data is on issue #4.
Test runs must not leave a ledger in the user's home.
During the worker runs something created ~/.freshtime/ledger.db with the real corpus (most likely a pi run without FRESHTIME_DB, not traced). It was deleted so Jeremy's first run is still a first run.
